# soseek 场景与决策归属

这是对 [主设计](../DESIGN.md) 的补充，状态均为设计。用户已确认云端中心、CLI + Skill、两人使用、开源自部署，并重申云端 Grok 编排是原有设想。该模式纳入首版目标；其他扩展场景不是额外实施或外部操作授权。

## 1. 按输入与交付选择流程

不要把所有请求都当成“给一句 query，返回搜索列表”。首先识别用户已经提供什么，以及最终要什么；由宿主 Agent 根据任务上下文填写操作、intent、过滤条件和预算。云端确保这些约束被执行。

| 场景与例子 | 已知输入 → 需要交付 | 谁决定下一步 | 组成能力与设计阶段 |
|---|---|---|---|
| 找准确原始出处：“某个 API 在这个版本到底怎么用” | 版本/报错/站点 → 对应版本原文与片段 | 宿主 Agent 用项目上下文判断 | search（域名/版本条件）+ read；首版基础能力 |
| 时效问题：“这周有哪些新的数据库发布” | 时间范围/地域/语言 → 时间明确的结果与来源 | 宿主给约束，云端路由 | news 操作或有验证过时间过滤的 search；扩展适配；不能把抓取日期当发布日期 |
| 已有 URL：“把这三篇文章读出来” | URL 列表 → 正文、抓取时间、失败清单 | 不需要研究 planner | read；批量参数需要独立限额；单 URL 首版，批量后续增量 |
| 同一主题的不同视角：“找这个方案的局限和失败案例” | 主张/子问题 → 支持、反例、未知点 | 宿主，或委托的云端 Grok | 分别查询/阅读再比较；首版研究目标，但不宣称自动保证事实正确 |
| 依据现有材料继续查：“已有五篇，还缺哪些来源” | 现有 run/source ID + 问题缺口 → 补充资料 | 宿主识别缺口 | 显式 source reuse / read source；拟定增量接口，避免隐式合并用户全部历史 |
| 找相似资料：“找和这个网页/项目相近的东西” | 已知 URL + 相似性要求 → 类似项目/页面 | 宿主说明相似维度 | provider-native find_similar 等；首版后段适配，不只是原样再搜标题 |
| 批量结构化调查：“十个产品各自的价格和限制” | 实体清单 + 字段 schema → 带来源表格与缺失值 | 宿主或显式云端研究 Agent | 按实体分组 search/read + extract；批量与模型抽取为候选扩展 |
| 单站收集：“抓某文档站这一章的所有页面” | 根 URL + 域/路径范围 → 页面集与覆盖报告 | 云端有界任务执行器 | map/crawl；后段适配；robots/站点限制、最大深度/页数、无法到达页面需可见 |
| 判断是否值得追加成本：“先给线索，再决定深挖” | 问题 + 初步结果 → 有依据地升级阅读范围 | 宿主或用户 | quick → 查看候选 → 有选择地 read；首版可组合，不自动复制整套 deep |
| 搜索复盘：“为什么这次只查了 Exa” | run ID → 路由/失败/耗时/用量解释 | 云端记录，宿主解释 | routing + attempts + usage；首版可观察性，不需要模型猜原因 |
| 复查已有结论：“上个月的结果现在还成立吗” | 保存的来源 + 日期 → 新旧内容及证据变化 | 宿主明确 fresh 和比较目标 | read/search fresh、版本与 diff；版本/差异是扩展，不将缓存旧结果当新查询 |
| 持续关注：“每周检查这些发布页有什么变化” | 主题/URL + 周期 → 新增、删除、实质变化 | 外部调度器触发，宿主/可选模型解释 | 未来监控集成；首版不建调度、通知和外部消息系统，本次不创建任何自动化 |

这些场景复用 search、read、provider-native operation 和 run/result。只有出现新的状态语义（如持续监控、批量恢复、结构化验证）才新增专用能力，不为每个场景都增加一条顶层命令。

## 2. 三种“自动”的区别

### 宿主已经是 Agent

Claude/Codex 知道用户正在做什么，可以拆题、设版本/日期条件、选择 search/read、发现遗漏后补查。soseek 云端负责凭据、执行、来源与费用，这个模式不需要再付钱让另一个模型重新规划同一个问题。

例如排查升级问题：宿主确定旧/新版本 → 找迁移指南 → 读具体章节 → 查 issue 解释仍未解决的差异 → 在本地结合代码形成回答。宿主无需把全部代码或聊天历史上传 soseek。

### 云端执行固定流程

`research --mode pipeline --profile deep` 显式选择固定流程：搜索→按排名和覆盖分配读页→取证据。它省去机械操作和多次网络往返，但不知道“结论冲突了，需要查发布日期或定义”。选择该模式时这些判断仍由宿主做。

选页依据是可检查规则，不叫模型“精读判断”：按子问题预留名额，再按融合排名、域名限制和正文预算选页；全部子问题不能覆盖时返回未覆盖项。可供分配的最小名额小于子问题数量时优先使用用户给定的优先级，无优先级则按输入顺序并显式说明，不把未读项默认为已覆盖。

### 显式委托云端 Agent

由云端 Grok 接收完整研究目标，按 plan → search/read → 更新证据与缺口 → 选择补查或 finish 循环；执行器给每一步设边界。这是首版目标，也是 research/answer 的设计默认，`--mode agent` 可显式表达。普通 search/read 仍可完全不经过 Grok。

Grok 也可独立充当搜索 provider：`search --provider grok` 使用其原生联网搜索；研究编排器可以把这项能力与 Exa/Tavily 等并列选择。普通搜索不启动 planner，不等于不能使用 Grok 搜索。imagen 现有线路可复用认证与 endpoint，但其图像模型不替代搜索模型。当前接法和实测边界见 [Grok 接入](GROK.md)。

必须明确 planner 的模型、目标、最大模型轮数、搜索/读取调用次数、token/费用/时间限制、是否允许使用原查询以外的新 query，以及停止条件。动态计划的预览展示可调用工具和预算 envelope，不能在执行前保证精确的未来查询、URL 或账单。

当前已验证现有 Grok 线路的原生搜索、结构化工具调用和一次真实外部工具闭环；自主多轮、复杂失败恢复与费用硬上界仍待实测。这是实现依赖，不能据此把目标降格为固定 pipeline。Grok 不可用时明确报告该模式未就绪，保留单家调用和显式固定流程；不做无提示替代，也不宣称已完成首版。

## 3. 不同意图下的路由不是同一排行榜

以下是需要评测的路由模板，不是已经核实的优劣结论或固定能力保证：

- general：先保留部署配置中的优先顺序；先验证可用，再用代表性任务比较质量与费用。
- news：候选必须支持所需时间/地域条件；比较 Tavily 新闻类与 Serper news 等实际支持的路径。
- papers：候选必须适合所需文献类型；比较 Exa 的论文分类、Serper scholar 等，保留 DOI/出版信息作为独立字段。
- exact/source：要求官方域或明确站点时，约束优先于引擎名；搜索返回第三方转述不能算满足原始来源要求。
- known URL：进入 read，比较内容提取能力与成本；不先做一次搜索增加费用。
- similar：由实际实现的原生相似检索操作参与，不把任何通用 search 都当成等价替代。

路由比较要控制同一问题、相同可满足的过滤条件、接近的采样时间和等价预算。某一类上胜出不自动升级为所有任务的全局默认。延迟故障统计能影响可用性调度，但不能替代相关性评测。

## 4. 融合的边界

首版去重是规范 URL 与已抓正文 exact hash，排序采用 RRF。多引擎高排名提高的是检索排序，不是事实真实性。标题类似、多个引擎都返回、多个网页转载同一篇稿件，都不能独立构成事实核验。

有三个不同输出不能混淆：

1. 候选列表：哪些页面值得看，如何发现和排序。
2. 证据包：实际读到了什么、来自哪里、哪些子问题没有材料。
3. 回答或判断：模型/宿主根据证据作出的综合，含冲突与不确定性。

全文语义去重、模型重排和自动事实核查是额外能力，需要与 URL/RRF 基线比较。Grok 研究模式中的 query 改写、选择引擎和补查则是明确委托的编排动作，纳入首版并按轮数/费用限制；它们不隐含在普通融合排序中。
